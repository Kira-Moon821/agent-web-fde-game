# 第 06 章 · 评测驱动开发（Eval-Driven）

> 岗位锚点：「评测运营」「Benchmark/Badcase 优化」「掌握大模型效果与性能评估方法」「负责过的指标」。
> 前置：03、04。 交付物：golden set + rubric + 通过线 + 回归门禁脚本。

## 1. 一句话立场

**没有评测的 AI 产品，等于没有测试的软件。** 而 AI 的特殊性在于：输出不确定，所以评测必须"抽样 + 分布 + 阈值"，不能"点对点断言"。

## 2. 四层评测体系

| 层 | 评什么 | 手段 | 频率 |
|---|---|---|---|
| L1 组件级 | 检索召回、工具调用正确率 | Recall@k、工具选择准确率 | 每次改动 |
| L2 端到端 | 最终答案质量 | golden set + rubric 打分 | 每次发版 |
| L3 性能 | 延迟、成本、并发 | P50/P95、单次成本、QPS | 每次发版 |
| L4 线上 | 真实用户满意度 | 点赞/追问率/转人工率/badcase 回流 | 持续 |

## 3. Golden Set 怎么建（这是核心资产）

- **规模**：60–120 条起步。少于 60 条，通过率波动 ±8 个点，没法判断改动是否有效。
- **构成**：常见问题 50% + 边界问题 25% + 应拒答问题 15% + 对抗/诱导 10%。
- **每条字段**：`id, 输入, 期望要点(非逐字), 必须包含的引用, 禁止出现的内容, 难度, 场景标签`。
- **来源**：真实日志 > 业务方提问 > 自己编。自己编的只能占 30%。

## 4. Rubric 怎么打分（可机械执行，才可回归）

五维加权，每维 0–4 分：

| 维度 | 权重 | 0 分 | 2 分 | 4 分 |
|---|---|---|---|---|
| 事实正确 | 35% | 关键结论错 | 大体对但有细节错 | 全对且有出处 |
| 引用支撑 | 20% | 无引用 | 有引用但不精确 | 逐条可点回原文 |
| 完整性 | 20% | 漏关键点 | 缺次要项 | 覆盖全部期望要点 |
| 格式合规 | 15% | 破坏 schema | 轻微偏差 | 完全符合 |
| 安全合规 | 10% | 越界/编造身份 | 边界表述含糊 | 有拒答/免责且恰当 |

**总分 = Σ(维度得分/4 × 权重) × 100**。通过线建议 **80**；关键场景（医疗建议、金额、法务）安全维度为**一票否决**。

### LLM-as-Judge 的正确姿势

- 用**与被测模型不同**的模型当裁判；给裁判 rubric 原文 + 期望要点，不给参考答案原文（防抄）。
- 裁判输出必须是结构化 JSON（分数 + 理由 + 引用位置）。
- **每周人工抽检 10 条**校准裁判，记录裁判与被测的一致性（Kappa 或简单一致率）。

## 5. 回归门禁（把它接进 CI，才算工程化）

```
改动 → 跑 golden set → 通过率 ≥ 基线 - 2pt 且关键场景 0 回归 且 P95 ≤ 阈值 且 单次成本 ≤ 阈值
     → 全过才允许合并/上线；否则打印 diff（哪些 case 由过转过不过）
```

**diff 比总分重要**：总分持平但 3 条关键 case 翻转，也是回归。

## 8.【一章一检验】

### L1 概念口试（8 问）

1. 四层评测各评什么，缺哪层最危险？
2. golden set 为什么必须包含"应拒答"和"对抗"样本？
3. rubric 里为什么"安全"要设一票否决？
4. 只报总分有什么问题？diff 怎么用？
5. LLM-as-judge 的三个已知偏差（位置/长度/自我偏好），各怎么缓解？
6. 通过率从 82% 降到 80%，你判不判回归？依据是什么？
7. P95 延迟和平均延迟，产品该盯哪个，为什么？
8. 线上 badcase 怎么回流成评测样本（谁标、怎么标、多久一次）？

### L2 代码闸门

```powershell
python ch06_eval/check.py
```

期望：`[CH06] PASS 7/7`。断言覆盖：golden set 字段完整、五类样本齐全、rubric 权重和为 1、v1 通过率计算与手工一致、v2 被门禁阻断且 diff 精确列出 2 条翻转、P95 计算正确、裁判输出为合法结构化 JSON。

### L3 交付物验收（5 项 × 20 分）

| 项 | 要求 |
|---|---|
| 金标集 | ≥60 条，四类构成比例合理，来源标注 |
| 判分器 | rubric 可机械执行，输出 JSON + 理由 |
| 门禁 | 一条命令给出 通过/阻断 + diff |
| 校准记录 | 人工抽检 10 条，记录裁判一致率 |
| 表达 | 1 页"我的评测口径"，能直接放进作品集 |

### 回炉清单

- 只有"感觉好多了" → 先建 60 条金标，再谈优化；
- 总分涨了但关键 case 掉了 → 把 diff 加进门禁；
- 裁判总给高分 → 换模型 + 给反例锚点 + 人工校准。

### 通关凭证

> "我建了 60+ 条金标与五维 rubric，并用回归门禁在 CI 里自动阻断了一次安全回归。"

## 9. 常见坑

- 金标集写成"标准答案全文"，导致模型只要措辞不同就判错 → 用"期望要点"而非逐字。
- 用被测模型自己当裁判（自我偏好，分数虚高）。
- 只看平均分，不看失败分布（一条致命错被 90% 的正确掩盖）。
- 评测跑一次就锁进抽屉，不做回归——那只是一次性报告，不是体系。
